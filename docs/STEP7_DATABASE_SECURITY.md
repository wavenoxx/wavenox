# Step 7 database and privacy security

## Effective permissions

`20261107145215_step7_customer_project_portal.sql` is additive and has not been applied to production. It requires the complete Step 1–5 migration history and Supabase Auth/Storage schemas. All ten new public tables enable and force RLS, with no browser-role policies and no PUBLIC/anon/authenticated table grants. The service role retains required SELECT/INSERT/UPDATE; project audit UPDATE is revoked and a trigger rejects audit UPDATE/DELETE. The application never exposes a service key to browser code.

The `project_private` schema is unavailable to browser roles. Two narrowly scoped SECURITY DEFINER helpers read verified Auth identity/email; both have empty search paths and service-only execution. Remaining project RPCs are SECURITY INVOKER with empty search paths and service-only EXECUTE. Privileged calls are reachable only after the HTTP boundary derives a verified actor; database helpers independently recheck active staff scope or confirmed non-staff identity and active project membership. This intentionally does not expose customer-scoped direct Data API interfaces.

Transactional entry points: `project_create`, `project_mutate`, `project_open_customer_session`, `project_document_access`. Reads/session/rate helpers: `project_read`, `project_list`, `project_customer_session`, `project_email_allowed`, `project_consume_limit`. Mutations and mandatory audit INSERTs commit together. Version conflicts map to HTTP 409; invalid transitions to 400; forbidden access to 403; unavailable storage/database to 503. A rollback never becomes an application success. Identical request IDs/payloads replay the committed result; conflicting replays fail.

The `project-documents` bucket is private. A restrictive storage policy denies anon/authenticated access even if an unrelated permissive policy exists. Server storage paths are UUID-derived, tied by constraint to the project/document ID, and never accepted through the generic mutation API. Downloads use authenticated server delivery with no-store, nosniff, attachment disposition and same-origin resource policy. Authorization is repeated after storage retrieval. Document metadata/audit is transactional; Storage and PostgreSQL do not share a transaction. Compensating cleanup prevents publication after failure, but crash/orphan reconciliation must be provisioned before live use.

## Evidence boundaries

Unit/domain/HTTP and adapter tests cover session separation, CSRF, strict payloads, viewer/coordinator denial, customer DTO privacy, revoked access, audit failure, replay, concurrent DEMO versions, unsupported scans, failed storage, invalid identity, no cookie after persistence failure and revocation during download. They are not proof of native RLS or provider delivery.

A disposable PGlite PostgreSQL preflight applies all migrations and executes project creation, notes, milestones, appointments, invitation approval and session acceptance. Its Auth/Storage schemas are fixtures and it is not native Supabase proof. The opt-in `scripts/step7-tests/database.test.ts` uses hard-coded loopback Supabase, real Auth, PostgREST and Storage, plus a fixture audit-failure trigger. It tests direct browser-role denial, two-customer isolation, banned users, staff scopes, rollback, native concurrency, replay, evidence requirements, appointment conflicts, private objects, OTP reuse, expired invitation/session, support privacy/rate limits and revocation. Nineteen native cases passed in [CI run 42557763076](https://github.com/wavenoxx/wavenox/actions/runs/42557763076) at implementation commit `19d6bd9a9ffa9a9422967d2b47dd40ce33065b0c`, alongside eleven inherited CRM cases. All seven tested personas are denied direct SELECT/RPC, project UPDATE, membership DELETE and forged audit INSERT attempts. Browser evidence is recorded separately in the execution report; no production authorization test was performed.
